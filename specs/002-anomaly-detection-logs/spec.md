# Feature Specification: 异常检测日志记录功能

**Feature Branch**: `002-anomaly-detection-logs`  
**Created**: 2025-01-27  
**Status**: Draft  
**Input**: User description: "添加日志的功能，之前异常检测时会有日志记录在 docker-compose-with-otel.yaml 中的异常检测服务里，现在的情况是只有检测到异常才会在 provider 中的日志中看到记录，我希望能够像之前一样看到所有异常检测执行的信息。由于现在已经没有独立的异常检测服务了，这些日志可以统一记录在后端服务的日志中；本次修改继续使用 002 分支，不创建新的分支，且所有描述文件内容全部使用中文。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 查看所有异常检测执行日志 (Priority: P1)

作为运维人员或开发者，我希望在异常检测 Provider 执行检测任务时，无论是否检测到异常，都能在日志系统中看到完整的异常检测执行信息（包括查询参数、数据获取情况、检测算法执行过程、统计结果等），从而能够像之前独立服务那样全面了解异常检测的运行状态，而不仅仅是在前端界面看到检测到异常后的结果。

**Why this priority**: 这是用户的核心需求，从独立服务迁移到 Provider 后，日志可见性下降影响了运维和调试能力。只有恢复完整的日志记录，才能确保迁移后的可观测性不降低。

**Independent Test**: 在工作流中调用 Anomaly Detector provider 进行异常检测，无论检测结果如何（正常、异常、无数据、数据不足等），都应在日志系统中（如 Loki、标准输出或 Keep 的日志聚合系统）找到包含检测参数、执行过程、数据统计和检测结果的完整日志记录。

**Acceptance Scenarios**:

1. **Given** 已配置并安装 Anomaly Detector provider，**When** 在工作流中调用该 provider 对某个 Prometheus 指标执行异常检测，**Then** 在日志系统中能够找到包含以下信息的日志条目：检测开始时间、查询的指标名称、数据源类型、查询时间范围、从数据源获取的数据点数量、检测算法类型、检测执行状态、统计信息（均值、标准差等）、检测结果（是否发现异常、异常数量）。
2. **Given** 上述场景中检测结果为"正常"（未发现异常），**When** 查看日志系统，**Then** 仍然能够看到完整的检测执行日志，包括"状态=正常"、"异常数量=0"等信息，而不仅仅是错误或警告级别的日志。
3. **Given** 检测过程中出现数据不足、查询失败等非异常情况，**When** 查看日志系统，**Then** 能够看到清晰的日志记录，说明数据不足的原因（如数据点数量少于最小要求）或查询失败的具体错误信息。

---

### User Story 2 - 日志格式与独立服务保持一致 (Priority: P2)

作为从独立异常检测服务迁移过来的用户，我希望 Provider 模式下的日志格式和内容与之前独立服务产生的日志在关键信息上保持一致或相似，以便能够使用相同的日志查询和分析方式，降低迁移成本。

**Why this priority**: 如果日志格式差异过大，用户需要重新学习如何查询和分析日志，增加了迁移的复杂度和学习成本。

**Independent Test**: 对比独立异常检测服务（如 `keep-anomaly-detector` 容器）的历史日志格式与 Provider 模式下的日志格式，确认关键字段（如指标名称、时间范围、检测结果、异常数量等）在两种模式下都能以相似的方式被提取和查询。

**Acceptance Scenarios**:

1. **Given** 独立异常检测服务在日志中记录了指标名称、查询时间范围、数据点数量、检测算法、异常数量等字段，**When** Provider 模式执行相同指标的检测，**Then** Provider 的日志中也包含这些相同或等价的字段，且字段命名和含义保持一致。
2. **Given** 用户使用 LogQL 或类似的日志查询语言在 Loki 中查询独立服务的异常检测日志，**When** 切换到 Provider 模式后，**Then** 用户能够使用相同或相似的查询语句查询 Provider 的异常检测日志，只需调整日志来源标识（如服务名称或标签）。

---

### User Story 3 - 日志可被前端界面或日志聚合系统收集 (Priority: P3)

作为系统管理员，我希望异常检测 Provider 产生的日志能够被 Keep 的前端界面、Loki 日志系统或其他日志聚合工具（如 ELK、Grafana）正常收集、索引和展示，从而能够通过统一的日志查看界面浏览所有异常检测活动，而不需要单独查看容器日志。

**Why this priority**: 统一的日志查看界面能够提高运维效率，避免在多个系统间切换查找日志。

**Independent Test**: 配置 Keep 系统使用 Loki 或其他日志聚合系统，执行包含异常检测的工作流，确认日志能够被正确收集并在日志查看界面中可见，且包含适当的标签和元数据以便过滤和搜索。

**Acceptance Scenarios**:

1. **Given** Keep 系统已配置 Loki 作为日志聚合系统，**When** 执行包含 Anomaly Detector provider 的工作流，**Then** 在 Loki 中能够查询到该 provider 产生的异常检测日志，且日志包含适当的标签（如 `provider=anomaly_detector`、`workflow_id=xxx` 等）以便过滤。
2. **Given** Keep 前端界面提供了日志查看功能，**When** 用户在工作流执行详情页面查看日志，**Then** 能够看到该工作流中异常检测步骤的详细日志，包括检测参数、执行过程和结果。

---

### Edge Cases

- 当异常检测执行时间很长（如查询大量历史数据）时，日志应记录开始和结束时间，以便分析性能问题。
- 当同一工作流中多次调用异常检测 provider 时，每条日志应包含足够的上下文信息（如工作流 ID、步骤 ID）以便区分不同调用。
- 当日志系统不可用或日志写入失败时，不应影响异常检测功能的正常执行，但应在可能的情况下记录警告信息。
- 当检测过程中发生异常（如 Prometheus 连接失败、数据解析错误）时，日志应记录详细的错误堆栈和上下文信息，以便排查问题。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须在 Anomaly Detector provider 执行异常检测时，无论检测结果如何，都记录包含以下信息的日志：检测开始时间、查询的指标/查询表达式、数据源类型（prometheus/tempo/loki）、查询时间范围、从数据源获取的数据点数量、检测算法类型、检测执行状态、统计信息（均值、标准差、最小值、最大值等）、检测结果（状态、异常数量、异常点详情）。
- **FR-002**: 系统必须在检测结果为"正常"（未发现异常）时，仍然记录 INFO 级别的日志，包含完整的检测执行信息和"状态=正常"、"异常数量=0"等结果信息，而不仅仅记录警告或错误级别的日志。
- **FR-003**: 系统必须在检测过程中出现非异常情况（如数据不足、查询返回空结果）时，记录清晰的日志说明原因，包括当前数据点数量、最小要求数量、查询表达式等上下文信息。
- **FR-004**: 系统必须在检测过程中发生错误（如数据源连接失败、查询超时、数据解析错误）时，记录包含详细错误信息和堆栈跟踪的 ERROR 级别日志，以便排查问题。
- **FR-005**: 系统必须为每条异常检测日志添加适当的元数据标签，至少包括：provider 类型（`anomaly_detector`）、工作流 ID（如果可用）、步骤 ID（如果可用）、租户 ID，以便在日志系统中进行过滤和查询。
- **FR-006**: 系统必须确保日志格式与 Keep 的日志标准保持一致，使用结构化日志格式（如 JSON），包含时间戳、日志级别、消息内容和额外的结构化字段（extra 字段），并统一输出到后端服务的日志管道中，而不是依赖独立的异常检测服务容器。
- **FR-007**: 系统必须在日志中记录检测算法的执行细节（如基线计算、阈值比较、异常评分等），至少对于 DEBUG 级别的日志，以便在需要时进行深度调试。
- **FR-008**: 系统必须确保日志记录不会显著影响异常检测的执行性能，日志写入失败不应导致检测功能失败，但应在可能的情况下记录警告。

### Key Entities *(include if feature involves data)*

- **异常检测日志条目**: 表示单次异常检测执行产生的日志记录，包含检测参数、执行过程、数据统计和检测结果等结构化信息，可被日志系统收集、索引和查询。
- **日志元数据标签**: 附加在日志条目上的键值对，用于标识日志来源（provider 类型、工作流 ID、步骤 ID、租户 ID 等），便于在日志系统中进行过滤和聚合查询。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在正常执行异常检测的情况下，100% 的检测任务都会产生至少一条包含检测结果（状态、异常数量）的日志记录，无论检测结果是否为异常。
- **SC-002**: 在日志系统（如 Loki）正常工作的前提下，用户能够通过日志查询语言（如 LogQL）查询到至少 95% 的异常检测执行记录，且查询结果包含完整的检测参数和结果信息。
- **SC-003**: 在包含异常检测步骤的工作流执行后，用户能够在 Keep 前端界面或日志查看工具中，通过工作流 ID 或步骤 ID 查询到该步骤的异常检测日志，成功率不低于 90%。
- **SC-004**: 日志记录功能不应显著影响异常检测的执行性能，在正常负载下，日志记录导致的性能开销不超过检测总执行时间的 5%。

## Assumptions

- Keep 系统已配置日志聚合系统（如 Loki）或标准日志输出机制，能够收集和展示应用日志。
- 用户具备访问日志系统的权限，能够通过日志查询工具或 Keep 前端界面查看日志。
- 日志系统具有足够的存储容量和索引能力，能够处理异常检测产生的日志量。
- 日志格式遵循 Keep 项目的日志标准，使用 Python 的 logging 模块或等价的日志框架，且异常检测相关日志与后端服务的其他日志通过同一日志管道收集和聚合。

## Dependencies

- 依赖 Keep 的日志基础设施（日志配置、日志聚合系统集成等），包括后端服务统一的日志输出与收集机制。
- 依赖 Anomaly Detector provider 的现有实现（`anomaly_detector_provider.py`），需要在现有代码基础上增强日志记录，使其通过后端服务的日志管道输出，而不是单独的异常检测服务。
- 如果需要在 Keep 前端界面展示日志，可能依赖前端的日志查看组件或 API。
